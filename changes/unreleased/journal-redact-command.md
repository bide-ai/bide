Section: Added

Added `bide journal redact`, the command that erases personal data from finished runs accountably, with `agent.Compactor` (implemented by `store/sqlite`) behind its storage step. It lists a plan as a dry run (each record by position, key, kind, length and leaf hash, never content, with a digest), and with `-execute -plan-digest` erases the records of a finished run into tombstones: it refuses a run that is not over, is leased (checked before anything is written), has a live parent, belongs to a session or has events in the event store (`-keep-event-copies` is recorded), refuses a run no verified signed journal head covers unless `-allow-uncovered` (recorded), and refuses a trail that does not match the heads in `-head-out` (a typo in `-trail-db`) or that holds records no earlier head attests (unless `-accept-unheaded-trail`). Every trail record is signed and bound to the deployment named by the required `-deployment`; the trail's head is signed with a key file and appended to `-head-out`, also after a failed pass. On SQLite the erasure runs with `secure_delete` on and the command then checkpoints and truncates the write-ahead log; when a reader holds the database open it says "STORAGE NOT COMPACTED" and exits 1 rather than claim success, and a test reads the database and WAL files for the erased bytes with another connection open. On Postgres the erasing role keeps its own DSN (`-redact-postgres-env`) because it can read nothing, the replaced row versions stay until the operator's `VACUUM` (the report says so), and an end-to-end test erases through that role and passes `bide audit redactions`. The trail is signed from the command line with a key file; HSM and KMS signing go through the library until `bide-hsm` gains it. The report ends with the copies the command cannot reach. There is no legal hold or second-person authorization yet.

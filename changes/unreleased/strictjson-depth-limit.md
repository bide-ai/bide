Section: Security

The strict JSON reader refuses a document nested more than 128 levels deep, before any decoder runs, and no longer rebuilds the path to each value at every level. In v0.8.0 and later, `strictjson.Check` rebuilt a path string like `$[0][0]...` at each level, so its time and memory grew with the square of the nesting depth: 30 KB of `[` took 0.8 s and 2.1 GB under `encoding/json` v1 (GOEXPERIMENT=nojsonv2), 100 KB took 12 s and 30 GB, and 16 KB took about 160 MB in the default build. Every reader built on it was affected: agent tool-call arguments (input the model controls) and typed answers, `plan.Load`, `plan.Validate` and `plan.InspectConfig` (config loading), `audit.UnmarshalStrict` (signed tree heads, evidence and journal exports), and the stop-policy and approval-item readers (`bide stop`, `bide approve`) and theme files. A deeper document now fails with an error naming the limit and the offset (`nesting deeper than 128 levels at offset N`), at constant memory. The deepest document bide itself reads or writes nests 5 levels (7 in the tests), so no valid input is affected; only a document built to be deeper than 128 levels is refused. A very large flat document still costs memory in proportion to its size, and `plan.LoadReader` and the audit export readers do not cap it: see KNOWN-LIMITATIONS.

The notifier now sends an all-clear. When an `outcome_unknown`, `approval_pending` or `recovery_failing` event that a receiver was, or may have been, told of stops being current (the halt was resolved, the gate decided, the run ended, recovery recovered), a `resolved` notification (`agent.NotificationResolved`) is delivered with the same audited claim and acknowledgement trail, at-least-once delivery, stable ID and retry as any event, so a PagerDuty incident, ticket or Slack thread can be closed. It names the event it ends in `Notification.Clears` (`Key`, `ID`, `Kind`) and the reason in `Notification.Reason`; in the webhook payload that is a `clears` object (`id`, `key`, `kind`, null on every other kind) and the existing `reason` field, and `deadline_at` is null. The ID of the event is final: a receiver treats every delivery of that ID, before or after the all-clear, as superseded, which is how an all-clear that arrives first is matched. It is never overdue (no deadline, no overdue notice) and is retried like any delivery. An event never claimed, and `run_aborted`, get none. It is found by a scan of the run's trail after every drive of a root run, every recovery pass and every unfinished run `NotifyPending` lists (one trail read each, off the drive's path), and, for a run that completed while nobody scanned, through the new open trail (`watch` and `unwatch` records, written before an event is observed and when nothing more is owed) that every sweep, `Recover` pass and `RecoverLoop` pass reads; it is kept in daily sealed segments `notify:@open:<date>` with checkpoints and a yearly index, so a read does not grow with history, and the first sweep or recovery pass lists events observed before it existed. A plan flow's run is now its own root on both the hook path and the sweep, so a flow whose ID holds a `>` files its gate under one trail. The `observed` record of a halt or approval gains `op_run`, `op_kind` and `op_id` (additive), so an ID too long to encode in the key can still be checked. Receivers that treated every webhook POST as a new alert should filter on `kind`. TLA+ model 14 gains the all-clear (`Clears`, key `r_<event>`) with its safety and liveness properties, regression configurations and the ordering limit (`limits/clear-before-event`). The open trail is verified for its time: every record is dated in its segment's UTC day, a seal may not skip an indexed segment, an index names segments of its year, and each segment is indexed in the index of its own year even when a writer repairs a gap. An open-trail record written by a process whose clock is behind its segment (another process's clock ran ahead and sealed into a later day) has its time moved later, never earlier, and keeps its own clock reading in a new `clock_at` field, which the verifier checks. During a rolling upgrade, any scan lists an event an older process delivered without listing it, and a second backfill pass after `WithNotifyUpgradeWindow` (a day by default; set it to how long your staged rollout takes) after the first (the first pass records the window in `backfill_window`, the checkpoint carries it with `backfills` and `backfill_at`, and the verifier requires the second pass no earlier than the first plus that window) lists what no scan reached. A panic in a `NotifyTrail` or `Notifier` now fails the round or call instead of the process, and a flush stops waiting for the catch-up scans and the backfill after ten seconds, so a slow trail store cannot hold a `Recover` pass.

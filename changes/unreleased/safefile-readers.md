Section: Fixed

A named pipe given where bide expects a file no longer hangs it: `bide view` (`-sth`, `-evidence`, `-approver-keys`, `-stop-policy`, `-pubkey` as a file), `bide edit` (a config swapped for a pipe after its check), `bide approve` (`-item`, `-approver-keys`, `-cert`, `-log-key`, `-verify-receipt`, `-tls-ca`), `bide stop -stop-policy`, `bide notify` (`-secret-file`, `-previous-secret-file`, `-client-ca`, `-cert` and `-key`, `-ca`), the webhook notifier's client certificate, key and server CA files, `bide approve -tls-ca`, `-client-cert` and `-client-key`, `bide journal redact` (`-pubkey`, the JSON and signed-head files they read), `bide identity` and the identity preflight (`-policy`, `-params`, `-expect`, certificate chains, the files a policy names) and `bide-anchor -pubkey` open the file without waiting for a writer and refuse anything but a regular file, with the reason; a directory is refused the same way. **Upgrading:** these flags no longer accept a path that names a named pipe, a device or any other file that is not a regular file. A process substitution (`-pubkey <(vault read ...)`) still works on unix, as does `/dev/stdin` and a `/dev/fd/N` path (`/proc/self/fd/N` on Linux): the form is matched as written, so a symbolic link to one is refused, and the stream is read up to the flag's size limit. `/dev/stdin` is standard input and is owned like `-`. A flag that carries a secret or a policy also takes `-` for standard input, and one flag only can read it in a run (a second is refused, naming both): `-pubkey` (bide view, bide journal redact, bide-anchor), `-sth`, `-evidence`, `-approver-keys` and `-stop-policy` (bide view), `-stop-policy` (bide stop), `-item`, `-approver-keys` and `-log-key` (bide approve), and `-secret-file` and `-previous-secret-file` (bide notify); bide approve needs `-yes` with any of them, since the confirmation would read standard input too. A file named `-` is written `./-`. Files that had no size limit now have one, and a file over it is refused with a message naming the flag and the limit: 1 MiB for `-pubkey` (bide view, bide journal redact, bide-anchor) and `-log-key`; 16 MiB for `-verify-receipt`, `-tls-ca`, `-client-cert`, `-client-key`, the `bide notify` secret, CA, certificate and key files, `-params` (bide identity and the preflight), `-policy` and the files a policy names, `-expect`, and bide journal redact's `-sth` and `-authorization`; and the signed-heads log (`-head-out`, bide journal redact) has no total limit, which would stop a log that only grows: it is read one head per line, and a head over 64 KiB is refused (the heads are held whole in memory, as before, because the redaction trail checks and signs over the full chain of prior heads: about 0.3 to 1 KiB each, so a 260 MiB log of about 650,000 heads takes a few hundred MiB). The limits already in place are unchanged (`-item`, `-approver-keys`, `-stop-policy`, `-cert`, bide view's `-sth`, `-evidence` and journals). The strict JSON reader's errors that name a field of a document (an unknown, duplicate or missing name, in a theme, policy, approval or tool-argument file) now quote at most 64 characters of the name, escaped, so a long name or an escape sequence in a file cannot flood or drive a terminal; a short name is still quoted whole, to help find the mistake. The library readers (`theme.Load` and the like) read regular files only, so what an error quotes comes from a file the caller could already read.

Section: Added

Added legal holds at the store: the optional `agent.Holder` capability (`PlaceHold`, `LiftHold`, `Holds`; `agent.Hold` names an ID, a matter, the runs it covers and whether it covers the sub-agent runs below them), implemented by `MemStore`, `store/sqlite` and `store/postgres`, with `storetest.Holder` as its conformance suite. A store's redaction now refuses a run an active hold covers (`agent.ErrRedactHeld`) in the same statement that would replace the record, so a hold placed while a pass runs either lands first or the record was already erased; `agent.PlanRedaction` names the holds that cover a run and refuses it (`RedactionPlan.Holds`). SQLite and Postgres keep the holds in a `bide_holds` table the migration creates (a file or schema from before holds has none and no hold). On Postgres the redaction function moves to `bide_redact_v3`, which reads the table as its owner, so the erasing role can neither read nor change it and a third role with `SELECT, INSERT, DELETE` on that one table places and lifts holds; the migration creates `v3` beside any older `bide_redact_v1` or `v2` (`v1` does not check holds), and revokes `EXECUTE` on every older version from PUBLIC and every role it was granted to (it never replaces or drops a function), and the store calls only `v3`, telling you to run the migration when it is missing. `v3` takes the holds table's `SHARE` lock first, so a placed hold stops every erasure that has not yet committed, and refuses to run unless its transaction is at `READ COMMITTED`: a role whose default isolation is stricter needs `ALTER ROLE ... SET default_transaction_isolation = 'read committed'`. There is no command for holds and no record of them in the signed redaction trail yet.

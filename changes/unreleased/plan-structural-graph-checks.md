Section: Fixed

`bide check`, `bide view -config` and `plan.InspectConfig` without a Registry now make every check `plan.Load` and `plan.Build` make on the wiring alone, so a config that `bide check` passed could not still fail to load for a reason that needs no Go code. New: a cycle that is not a loop, a node not reached from the entry (worded so it reads as work in progress: a node you have declared and not wired in yet is a config that will not load), a node fed by several producers without a join, join inputs on mutually exclusive arms of a switch or that a switch can skip, and the shape of a loop's body (no inner switch or nested loop, no edge leaving or entering it past its head, no node between the head and the switch that is not on the loop path). They are Build's own checks run over a spec with no types, in Build's order; with a Registry nothing changes (Build makes them itself, after the type checks). Upgrading: a config with one of these now fails bide check, and the editor shows it as a config error until it is wired. The examples had one: examples/plan/flows/refund-policy-bypass.yaml, the policy-bypass demo that the run viewer guide, bide sample (flows/refund-bypass.yaml) and bide check -diff use, routed a vip arm straight to `charge`, which made `charge` fed by two producers, a config plan.Load has always refused; the earlier bypass example was a config Load refuses; it is now one that loads, with the bypass routed to an ungated node: the vip arm reaches a second charge step (`charge_vip`, block charge), so the violated assertion is now "every path to charge_vip passes approval >= 2 of 3" with the counterexample validate -> lookup -> charge_vip. A bypass of a gate on the same step cannot be a loading config, because a step with several producers needs a join.

`bide edit`'s assertions panel lists the config's `assert` lines with their verdicts and counterexamples and adds, edits and removes them from the six forms of the grammar as templates (every path to a node passes an approval gate of at least K [of N] [excluding the requester], every path to a node passes another node, every path to a terminal passes a node, no side effect after a node, a node reachable, a node unreachable). The page sends the form's parameters and the server writes the line the check reads (`flowedit.Assertion`, `Assertion.Text`, `ParseAssertion`), quoting a node name with a space and refusing one the grammar cannot hold; only declared nodes can be chosen and a line the config already has is refused. Each change to the form asks the server what the check says of the line and shows its verdict, with the counterexample path of a violation, before anything is added. Add, set and remove are splices (`add_assertion`, `set_assertion` and `remove_assertion` of `flowedit.ApplyOperation`; removing the last line takes the list), so a comment above a removed line goes with it. The panel says assertions are checked in CI and not at run time; `POST /api/apply` answers a refused operation with a 200 and `{"refused": reason}` instead of an error status, so asking what an operation would do does not fill the browser console with failed requests.

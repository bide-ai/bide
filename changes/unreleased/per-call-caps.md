Section: Added

Per-call amount caps: `agent.WithCaps(lines...)` declares rules on a tool (`name: tools.argument[minor, currency=member] > 500 USD -> refuse`), and `ToolSpec` carries `Caps` for a tool that builds its own spec. The rules are checked against the tool's input schema when the tool is registered (an argument the schema lacks, one that is an array, object or boolean, a currency member that is not a string, a limit above 2^53 minor units, a rule with `-> gate` or `-> gate(name)`, which arrives with the escalation gate, and a cumulative `sum` rule, which needs the cap ledger, are `ErrConfig` and "not yet supported"), and every call is decided twice: on the arguments the model sent, before any gate or claim, where a refused call is answered with a tool error that names the rule and gives no figure, and again on the arguments the tool will receive after any tool middleware, where a call a middleware pushed over the limit is refused before the call begins. An amount that cannot be read with certainty (negative, absent, an exponent form, too many fraction digits, or arguments with a repeated or case-variant member) gets the rule's action, and a currency no rule covers gets the strictest action among the argument's rules, compared byte for byte; no float is used. The reasons are recorded in `gate-reason:<call>`, which can add a requirement and never remove one. A tool that carries caps cannot be a plan flow block: `plan.Registry.RegisterTool` and `Builder.Tool` return `ErrConfig`. See [amount caps](docs/guides/amount-caps.md) and the limits in `KNOWN-LIMITATIONS.md` (array shapes, no conversion, no totals). Break risk: none for existing code; the new `ToolSpec` field is nil for a tool that does not use it.

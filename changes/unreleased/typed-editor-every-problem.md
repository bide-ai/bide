Section: Fixed

Before release, `bide edit` against a Registry or a blocks description let an edit through that added a second problem of a kind the text already had: the config check (`plan.InspectConfig`, `plan.InspectConfigDescribed`) reported only the first type misfit, and the first of each wiring problem (a loop's shape, a node not reached from the entry, a join's routes), so the typed editor, which refuses an edit that adds a type problem or a loop-shape error by comparing the problems before and after, saw nothing new when a second one appeared. The check now reports every one of them: every edge, switch arm, join input and terminal whose types do not fit, up to 100 with a final line saying how many more there are, and every refusal of the wiring checks. `plan.Load` and `plan.Validate` list all the type problems in their error instead of the first. `bide check` and the viewer show the longer lists. Where there are several problems the first still leads, so a message or an error that began with it still does; `plan.Load` and `plan.Validate` errors, which name the first problem as before, now go on to name the others after it. The editor compares the complete lists of type problems, not the first 100 a report lists, so an edit cannot hide a new problem past that cap. The refusals of `plan.Load` and `plan.Validate` (type problems and the checks Build makes) now wrap `agent.ErrConfig`, so `errors.Is(err, agent.ErrConfig)` holds for them as it does for the other config errors; their text is unchanged. The editor identifies a problem by its message with the full names and without the position of its wiring element (not by the shortened text it shows), so two problems whose names differ only past the 64th character are two, and moving an element does not make an old problem new; and the type problems and the loops' shape are found even when the config has another error (an unknown name, a safety above the registered one), so that error no longer hides them.

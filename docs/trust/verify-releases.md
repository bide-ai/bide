# Verifying releases

Every release of the `bide` command carries three independent kinds of evidence, so you can decide what to trust before you install it:

1. **A signature** on `checksums.txt` and on each archive, made keyless with [cosign](https://docs.sigstore.dev/cosign/signing/signing_with_blobs/) using the release workflow's GitHub OIDC identity. There is no long-lived signing key to steal or rotate; the signature proves that the file was produced by the `release.yml` workflow of `bide-ai/bide` for that tag, and the signing event is recorded in the public Sigstore transparency log (Rekor).
2. **An SBOM** per archive (`<archive>.sbom.json`, SPDX JSON, generated by [syft](https://github.com/anchore/syft)), listing the Go modules compiled into the binary.
3. **Reproducibility**: the binaries rebuild byte for byte from the tag (`scripts/repro.sh`), which the release workflow checks on another operating system for every release.

What is covered, precisely: the signatures cover the archives, `checksums.txt` and `approve-page.SHA256SUMS`; `checksums.txt` lists every archive and SBOM. The signature establishes where and when a file was built and by which workflow. It does not establish that the source is free of defects, and it does not cover the Go modules published for `go get`, which the Go module proxy and checksum database authenticate separately.

Signing and SBOMs apply from the first release made after they were added to the release workflow. A release with no `*.sigstore.json` files was published before that.

## What a release contains

For a version `X.Y.Z` and each of linux, darwin, windows on amd64 and arm64:

| File | What it is |
|---|---|
| `bide_X.Y.Z_<os>_<arch>.tar.gz` | The archive: `bide`, `LICENSE`, `NOTICE`, `README.md` |
| `bide_X.Y.Z_<os>_<arch>.tar.gz.sigstore.json` | Cosign bundle for the archive: signature, certificate, transparency-log entry |
| `bide_X.Y.Z_<os>_<arch>.tar.gz.sbom.json` | SBOM of the archive (SPDX JSON) |
| `checksums.txt` | SHA-256 of every archive and SBOM |
| `checksums.txt.sigstore.json` | Cosign bundle for `checksums.txt` |
| `bide.rb` | The Homebrew formula, generated from `checksums.txt` |
| `approve-page.SHA256SUMS` | SHA-256 of each file of the approve page bundle (`approvals/cmd/approvepage`), in `sha256sum -c` format |
| `approve-page.SHA256SUMS.sigstore.json` | Cosign bundle for `approve-page.SHA256SUMS` |

## Verify a download

Install [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) (v2.4 or later, or v3), then, with the release's files in one directory:

```sh
VERSION=X.Y.Z                       # the version without the leading v
TAG=v$VERSION
ARCHIVE=bide_${VERSION}_linux_amd64.tar.gz

# 1. The checksum file was signed by bide's release workflow for this tag.
cosign verify-blob \
  --bundle checksums.txt.sigstore.json \
  --certificate-identity "https://github.com/bide-ai/bide/.github/workflows/release.yml@refs/tags/$TAG" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  checksums.txt

# 2. The archive is the one the signed checksum file names.
sha256sum --ignore-missing --check checksums.txt      # macOS: shasum -a 256 --ignore-missing --check checksums.txt

# 3. Optionally, the archive's own signature.
cosign verify-blob \
  --bundle "$ARCHIVE.sigstore.json" \
  --certificate-identity "https://github.com/bide-ai/bide/.github/workflows/release.yml@refs/tags/$TAG" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  "$ARCHIVE"
```

Each `cosign verify-blob` prints `Verified OK` and exits 0 on success; any other result means do not install. Pin the identity to the tag you intended to install: a signature for a different tag, repository or workflow does not match. To accept any release of bide rather than one tag, use `--certificate-identity-regexp '^https://github.com/bide-ai/bide/\.github/workflows/release\.yml@refs/tags/v'` instead of `--certificate-identity`, and know that it accepts every tag.

If your cosign is older and does not read the bundle format, upgrade it; the bundle is the Sigstore bundle format that current cosign writes and reads.

Homebrew users: the formula pins the archive checksums of the release (`brew install bide-ai/tap/bide`), so Homebrew verifies the archive against a checksum taken from the signed `checksums.txt`; you can still verify `bide.rb`'s checksums against the signed file. `go install github.com/bide-ai/bide/cmd/bide@vX.Y.Z` builds from source and is verified by the Go checksum database, not by these signatures.

## Verify the approve page bundle

An organization that hosts the approve page ([human approval guide](../guides/hitl-approval.md)) serves files that sign approvers' decisions, so it checks them before it deploys. Subresource Integrity in the page's `index.html` pins its script and stylesheet, but no browser mechanism pins the entry document itself, so each release publishes the SHA-256 of every file of the bundle, signed like `checksums.txt`. The release workflow builds the bundle from the tag, and its `repro` job rebuilds it on macOS and fails unless the sums match byte for byte.

```sh
TAG=vX.Y.Z
gh release download "$TAG" -R bide-ai/bide -p 'approve-page.SHA256SUMS*'

# 1. The sums were signed by bide's release workflow for this tag.
cosign verify-blob \
  --bundle approve-page.SHA256SUMS.sigstore.json \
  --certificate-identity "https://github.com/bide-ai/bide/.github/workflows/release.yml@refs/tags/$TAG" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  approve-page.SHA256SUMS

# 2. The bundle you deploy is the one the signed sums name, file for file.
go run github.com/bide-ai/bide/approvals/cmd/approvepage@$TAG -out ./site
cmp site/SHA256SUMS approve-page.SHA256SUMS
(cd site && sha256sum --check --strict SHA256SUMS)   # macOS: shasum -a 256 --check --strict SHA256SUMS
```

Run step 2 against the files you actually serve, at deploy time and whenever they are changed. `config.json` is the deployment's own file and is not in the sums; it is protected content (see the guide). The approve page first ships in v0.17.0, the first release that publishes these sums.

## Reproduce the binary

Signatures prove who built a file; reproduction proves the binary matches the source.

```sh
git clone https://github.com/bide-ai/bide && cd bide
scripts/repro.sh vX.Y.Z      # downloads the release, checks it against checksums.txt, rebuilds each binary, compares bytes
```

It exits non-zero if any binary differs. Together the three checks (signature, checksum, reproduction) reduce trust in a downloaded `bide` to trust in the source at the tag and the Go toolchain.

`bide-hsm` (`bide approve` for keys in an HSM or a KMS) is not in the release archives, so none of this applies to it. It needs cgo, so a prebuilt binary would be only as reproducible as the C toolchain behind it, which the release does not pin for each operating system and architecture; the pure-Go `bide` binary keeps the guarantees above. Build `bide-hsm` from source, `CGO_ENABLED=1 go install github.com/bide-ai/bide/cmd/bide/bide-hsm@vX.Y.Z`, which the Go checksum database verifies. Two builds of it with `-trimpath -buildvcs=false` from copies of the tree at different paths with one toolchain were byte-identical when tried on one machine; without `-trimpath` (which a plain `go install` does not pass) they differ, and none of that is a claim about other toolchains.

## Read the SBOM

```sh
jq -r '.packages[].name' "$ARCHIVE.sbom.json"                   # modules compiled into the binary
grype sbom:"$ARCHIVE.sbom.json"                                  # scan it for known vulnerabilities, if you use grype
```

The SBOM is SPDX 2.3 JSON. It lists the Go modules recorded in the binary's build information, with versions. It is a point-in-time inventory of the release, not a statement that those dependencies are free of vulnerabilities. The audit-only build (`-tags bide_audit_only`) has a much smaller dependency set (the standard library and the core module); if that is all you need, build it from source and compare ([security model](../guides/security-model.md#offline-verification)).

## For maintainers

The signing identity is the `release.yml` workflow at the release tag, so it works only for releases made by that workflow with `id-token: write`. The workflow verifies every signature after publishing (the `verify-signatures` job), and fails the run if one does not verify. The manual dry run (`workflow_dispatch`) builds SBOMs but skips signing so it leaves nothing in the public transparency log. To check the configuration locally: `goreleaser check`, and `goreleaser release --snapshot --clean --skip=sign` (needs `syft` on the path).

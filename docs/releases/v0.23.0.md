**Limit the money one tool call can move, and test bide under Go's FIPS 140-3 mode.**

v0.23.0 adds amount caps to the engine: a rule in your Go registration that refuses a tool call over a limit, whatever the model sent. It also turns on a CI job that runs the test suite under `GODEBUG=fips140=only`, fixes three paths that panicked there, and closes a gap in which a tool wrapper could silently drop an approval gate. Caps and the untrusted-content marks are experimental: their Go names may change in a minor release.

- **Amount caps (refuse only).** `agent.WithCaps` puts a rule on a tool, for example `big_refund: refund.amount[minor, currency=currency] > 500 USD -> refuse`, and `ToolSpec.Caps` carries it for a tool that builds its own spec. Rules are checked against the tool's input schema when the tool is registered. Every call is decided twice, on the arguments the model sent and again on the arguments the tool will receive after any tool middleware. A call over the limit is not run and not asked: the model reads a tool error that names the rule and gives no figure, and the figures are in the journal. An amount that cannot be read with certainty gets the rule's action. A cumulative form, `sum 5000 USD per day [by key] -> refuse`, counts each call's amount in a cap ledger (a journal run under `@cap/`, namespace set with `agent.WithCapNamespace`) before the tool begins; a store that cannot be read or written fails the call, so a cap fails closed. The loop releases the slot of a call it proved never began, and `Recover` and `RecoverLoop` release the slot of an attempt recorded as not started (in windows still open); nothing else is released, so a window only over-counts. `-> gate` is refused at registration: holding a call for approval arrives with the escalation gate. No currency conversion, no arrays, no totals across tools. A tool that carries caps cannot be a plan flow block. See the [amount caps guide](https://github.com/bide-ai/bide/blob/v0.23.0/docs/guides/amount-caps.md); the stripe-refund example adds one cap rule over both its refund tools (`-max-refund`).
- **Untrusted-content marks (experimental, inert).** `agent.Untrusted(source)` declares that a tool's results are untrusted content, and the engine records the source with every result of that tool (`Safety.Untrusted` of the result record, denials, errors and a saga's failure record included). `agent.WithUntrustedInput` and `agent.WithTrustedInput` state where a run's input came from in `run:start`'s settings, and a later drive that passes another is `ErrConfig`; `agent.RetrievalUntrusted` marks a retrieval layer's step; `agent.TaintExempt(reason)` is a Go-only exemption declaration that does nothing yet. A source or reason is a non-empty, printable UTF-8 name of bounded length. The marks are recorded with or without a taint policy and **nothing acts on them in this release**: no call is gated, held or refused because of one. A mark is evidence, not a control. A run that states nothing records exactly what it did before, and older binaries ignore the new members. See the [untrusted content guide](https://github.com/bide-ai/bide/blob/v0.23.0/docs/guides/untrusted-content.md).
- **FIPS 140-3 mode in CI.** A "Test (FIPS 140-3)" job runs the Go tests with `GODEBUG=fips140=only` against Go's in-tree module and module v1.26.0 (in the merge queue, on main and on labelled pull requests) and against module v1.0.0 (on main). Under v1.0.0, which has no ML-DSA, it skips only the tests listed in `.github/fips-v1.0.0-excluded.txt`. It is not a required check, and some suites do not run under the mode (SoftHSM2 and PKCS#11, MinIO Object Lock, the cloud emulators, the browser suites); the [security model](https://github.com/bide-ai/bide/blob/v0.23.0/docs/guides/security-model.md#post-quantum-and-hybrid-signatures) lists them. This tests bide's behaviour in Go's FIPS mode. bide makes no claim that it, or any module it runs on, is FIPS validated.
- **`bide edit` fixes.** Removing a node removes the `assert` lines that name it (the dialog lists them, the weakened banner names each, Undo restores them). An `assert` line the grammar cannot read is judged to name a node by one rule, whatever punctuation surrounds the name. Renaming a gated node no longer reads as a weakening when it is combined with another change to that node; a rename together with a lowered need, a lowered safety, a removed gate or a removed assertion is still reported.

Security:

- A tool wrapper (a tool with an `Unwrap() Tool` method) can no longer hide a gate it wraps. `agent.New`, `agent.With` and the plan registry's `RegisterTool` now refuse, with `ErrConfig`, a wrapper whose own `Spec` is weaker than a tool on its `Unwrap` chain, however the wrapper holds that tool. Before, a wrapper that kept the tool in a named field and wrote its own `Spec` was accepted, the outer `Spec` won, and the approval gate or timeout of the wrapped tool silently did not apply. See Upgrading.
- A decorator that embeds a capped tool, or a tool with an `Untrusted` declaration, and writes its own `Spec` without it is refused at registration, as one that hides an approval gate or timeout already was, and so is a wrapper on an `Unwrap` chain that does not carry the wrapped tool's `Untrusted` declaration (the option, or a source in `Safety`). Only the presence of the declaration is compared: a different source name on the wrapper is accepted.
- Three paths no longer panic under `GODEBUG=fips140=only`: importing `govern/redislog` (go-redis hashed its script with SHA-1 in package init; Redis now computes the digest), verifying an RFC 3161 token that carries a SHA-1 `signingCertificate` attribute (DigiCert's tokens do; the consistency comparison is still made), and a webhook secret shorter than 14 bytes (see Upgrading).
- Correction: the documentation said FIPS mode and ML-DSA are mutually exclusive. That holds only for Go's FIPS 140-3 module v1.0.0, where `crypto/mldsa` is unavailable and selecting ML-DSA or hybrid is an error, not a panic. Under module v1.26.0 and later ML-DSA and hybrid signing work under `GODEBUG=fips140=only`. The security model, control mapping, threat model, operations and audit guide now say so by module version.

Fixed:

- `bide edit`: removing a node left `assert` lines that name it behind to report as broken; renaming a gated node beside another change to it was mishandled; an `assert` line the grammar cannot read was judged by an inconsistent rule (see above).
- A wrapper whose `Unwrap` returns a typed nil pointer no longer panics registration or sub-agent lookup; it ends the chain.

    go install github.com/bide-ai/bide/cmd/bide@v0.23.0

API changes:

- Added: `agent.WithCaps`, `agent.WithCapNamespace`, `ToolSpec.Caps`; `agent.Untrusted`, `agent.TaintExempt` (declared, does nothing yet), `agent.WithUntrustedInput`, `agent.WithTrustedInput`, `agent.RetrievalUntrusted`, `ToolSpec.Untrusted` and `ToolSpec.TaintExempt`; `agent.ErrToolUseIDInvalid`, `agent.IsReservedRun`, `agent.IsCapRun`, `agent.IsReservedStepName`; `notify.ErrShortSecret` and `notify.CheckSecret`; `flowedit.Rename`, `flowedit.CompareRenamed`, `flowedit.Weakening.Renamed` and `flowedit.Edited.Renames`. The generated [API reference](https://github.com/bide-ai/bide/blob/v0.23.0/docs/reference/api/index.md) lists every symbol.
- Changed: `notify.WithSecrets`, `NewWebhook`, `Verify`, `VerifyBody`, `Sign`, `relay.New` and the `bide notify` verbs refuse or leave out a secret shorter than 14 bytes under `GODEBUG=fips140=only` (unchanged otherwise); `relay.RejectionClass` has a case for it.

Upgrading:

- **Wrappers.** A tool with an `Unwrap() Tool` method whose `Spec` drops or loosens what the tool it wraps declares is now `ErrConfig`: no approval gate; fewer decisions needed; a `SingleApproval` over an m-of-n gate; an approver the wrapped gate does not name; no `ExcludePrincipal` where the wrapped gate has it; no gate deadline, or a longer one; no `Timeout`, or a longer one; a cap rule line the wrapped tool has and the wrapper does not carry word for word. Declare the same on the wrapper, or build its spec from the wrapped tool's. A wrapper with a different name cannot carry a rule line that names only the wrapped tool: write one line naming both tools (`refund|refund_logged.amount[...]`) and carry it on both. A wrapper that does not carry the wrapped tool's `Untrusted` declaration is refused too (only its presence is compared). `Safety` is not compared through the chain, and a wrapper with neither embedding nor `Unwrap` cannot be seen through: declaring them is still the wrapper author's duty.
- **Reserved names.** Run IDs that start with `@cap/` are reserved for cap ledgers: `Run`, `Stream`, `RunTyped`, `Session` and the exported calls that write records to a run you name return `ErrConfig` for one, and `Recover`, `RecoverLoop`, the notification sweep, the run viewer, `bide approve -list`, `bide audit notifications` and `bide audit redactions` skip it. If you already run a run ID under `@cap/`, rename it before upgrading, or a gate waiting in it will not be shown to an approver. A `Step`, `Parallel` or `ResolveHalt` name that starts with `slot:`, `cap-intent:`, `cap-reserve:` or `gate-reason:` is reserved as well and fails with `ErrConfig`, and so does one that starts with `taint/`.
- **Tool-use IDs.** A live model turn whose tool-use ID contains `#` now fails with `agent.ErrToolUseIDInvalid` (it wraps `ErrModel` and `ErrProtocol`, so `middleware.Retry` retries it, and the rejected turn is not journaled). A model server that sends `#` in a tool-use ID fails every turn that calls a tool. Resuming a journal that already holds such an ID does not re-check it, but `agent.Replay` used as the model of a new run fails on a recorded `#` ID.
- **Webhook secrets under FIPS.** With `GODEBUG=fips140=only`, `notify.NewWebhook` returns `agent.ErrConfig` for a secret shorter than 14 bytes, `relay.New` and the `bide notify` verbs refuse it at start, `Verify` returns `ErrShortSecret`, and a delivery a secret cannot sign is not sent. Without that mode any length is accepted as before. Use 32 bytes or more.
- **Caps.** A tool that carries caps cannot be registered as a plan flow block (`plan.Registry.RegisterTool` and `Builder.Tool` return `ErrConfig`), and neither can a tool that carries an `Untrusted` or `TaintExempt` declaration. A cumulative rule keeps the reservation of a call that may have run, of an `Idempotent` call that was refused or cancelled, of a `ResolveHalt`ed call and of a saga's rollback until its window ends, so a window only over-counts, and a tumbling window allows up to twice the limit across a boundary. A key with a byte outside ASCII is refused: normalise it in your tool.
- **Marks.** A `Step` option `WithSafety` whose `Safety` names an untrusted source is `ErrConfig`: a Step is not a tool and its result carries no mark; declare the source on a tool with `agent.Untrusted`.
- Nothing else changes for existing flows and gates; a deployment that declares no cap and no untrusted source records exactly what it did.

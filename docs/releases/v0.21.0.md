**The pieces a bank pilot asks for: certificate-bound approver onboarding, accountable erasure with legal holds, a kill switch, a locked anchor in S3, and build provenance for the release itself.**

v0.21.0-rc.1 preceded this release, and this page lists everything since v0.20.0. v0.21.0 is the first release written against a bank's review questions: who can approve and how is that checked before go-live, how is personal data erased without losing the audit evidence, how is every agent stopped at once and how is that stop evidenced, where do signed heads go so that the operator cannot rewrite them, and how is the binary known to come from the release workflow and a builder bide's own repository cannot alter. Each part below says what is built, what is experimental, and what is still open. The decision layer (typed decision models and rules whose output can only make bide stricter) is designed and accepted ([design note](https://github.com/bide-ai/bide/blob/v0.21.0/docs/design/decision-layer.md)) and planned for v0.22.0; nothing of it is in this release. The kill switch, erasure (redaction) and legal holds are labelled experimental in this release: their Go API and command flags may change in a minor release, with a changelog entry, and their records follow the pre-1.0 format policy of every other artifact (a verifier reads only the current format; an export under an older tag fails with `audit.ErrFormat`, and a single stop record under another tag is rejected). The tombstone format, `Record.Redacted` and the leaf hash it keeps are core, because they are part of the store contract. The guarantees the guides state hold under the label (see [stability](https://github.com/bide-ai/bide/blob/v0.21.0/docs/trust/stability.md#package-stability)). `anchor/awss3`, the new `audit/anchorobj` and `audit/crlrefresh` are experimental too, and the certificate-bound approver checks are core. [docs/KNOWN-LIMITATIONS.md](https://github.com/bide-ai/bide/blob/v0.21.0/docs/KNOWN-LIMITATIONS.md) lists the open items in full. Nothing here is a certification: the new [control mapping](https://github.com/bide-ai/bide/blob/v0.21.0/docs/trust/control-mapping.md) says what bide provides for each framework it names, what the institution must still provide, and what is not covered. There has been no external security review.

- **Onboarding certificate-bound approvers.**
  - *Pre-flight.* `bide identity check` is for the platform team to run before go-live and for an approver to run when a decision is refused. It reports one line per check with the fix (or JSON with `-json`): the policy file and its pinned CAs; the declared CA timings; whether the policy file and `-params` agree member by member with the policy record the gate journals; whether the CRLs are fresh by the refresher's health model; and, for an approver's chain (`-cert`), whether the gate would accept it, using the same function the gate calls (`audit.CertApprover.CheckCertificate`). It never reports ready while a part was left out (`-no-status` and `-no-expect` give a partial result, exit 4), and every report lists what a pre-flight cannot check ahead of time. `cert.cdp` catches the case where a CA's issuing distribution point (what step-ca stamps) means none of the CRLs covers the leaf, so the gate would wait.
  - *Keys in an HSM or KMS.* `bide-hsm csr -key <ref>` writes a PKCS#10 request for a key held in PKCS#11, AWS KMS, Google Cloud KMS or Azure Key Vault. With `-policy <file> -as <approver>` it asks for exactly what the gate's identity policy looks for. It checks its own request before writing and never overwrites a file without `-force`. Ed25519 and P-256 only; there is no RSA request. `bide keygen -csr` shares the code, and both take `-cn` for CAs that refuse an empty subject.
  - *Single sign-on.* A worked recipe, `docs/guides/sso-certificates.md`, and a tested example module issue short-lived approver certificates after an SSO login with step-ca as the reference CA. The test runs the real login, a refused login without MFA, a revocation and the refused decision after it, in the Integration job; the guide says what it does not cover (an HSM or KMS key, another identity provider, other CAs).
  - *CRLs.* A CRL that step-ca signs with an issuing distribution point holding only a URI is now read instead of refused, and it counts as evidence of absence only for a certificate whose own distribution points name that URI. The `-params` file takes the remaining members of the policy digest, so `bide identity check -expect-digest` is a true equality when it states them all. Error messages and start-up events now say why a CRL was refused and why the printed digest cannot equal the gate's when the file lacks members.
  - *Approving.* `bide approve -item FILE` decides a call from the output of `bide approve -list -json`, so a call whose id holds a line break or an invisible character can be decided from the command line. The fallback text for such ids now says what to do.

- **Erasing personal data, with evidence and legal holds (experimental).**
  - *The command.* `bide journal redact` lists a plan as a dry run (each record by position, key, kind, length and leaf hash, never content) and, with `-execute -plan-digest`, replaces the records of a finished run with tombstones that keep the position and the audit leaf hash. It refuses a run that is not over, is leased, has a live parent, belongs to a session or has no verified signed head covering it (`-allow-uncovered` is recorded), and a held run. On SQLite it erases with `secure_delete`, truncates the write-ahead log and says "STORAGE NOT COMPACTED" with exit 1 when it cannot. On Postgres the erasing role can read nothing, and the replaced row versions stay until the operator's `VACUUM`. The report ends with the copies the command cannot reach.
  - *The evidence.* Each pass appends a begin and an end record to a redaction trail signed with the redaction key and bound to a deployment name. `bide audit redactions` finds a deleted or reordered trail record, an erasure made by hand, a tombstone whose name or hash differs from the trail's, a pass with no covering head, and an erasure that began under a hold. `bide journal acknowledge` records, signed and bound to its position, that a named record the tool did not write was reviewed, so the audit reports it as acknowledged and not as a failure.
  - *Legal holds.* `bide journal hold place|lift|list` records a hold in the store and in the signed trail (the lift is recorded first), and a store refuses to erase a held run in the same statement that would replace the record. `bide audit redactions` compares the trail's holds with the database's.
  - *End markers.* A redaction can erase a run's end marker by name (`-name run:complete`), so a final answer or a failure text can be erased. A tombstone at an end marker counts as an end of unknown kind: readers find the run over and none reads how it ended from the journal, because a tombstone's name is outside the leaf hash. `bide audit redactions` prints how the run ended (`run r1: ended: completed (per trail)`) when the signed redaction trail accounts for the marker by name, leaf hash and time. The lifecycle model (model 10) covers the erasure.
  - *A second person for a lift.* `bide journal hold authorize` has a second person sign, with a key of their own (a key file, or an HSM or KMS key through the new `bide-hsm journal`), their consent to lift one hold, bound to the hold as it stood, the placement's trail position, the deployment and a validity. `bide journal hold lift -authorization FILE -authorizer-pubkey KEY -require-authorization` checks it before anything is written and embeds it in the lift's signed record. The authorizer's key must not be the trail's signing key or share a component with it. `bide audit redactions` checks the embedded authorization offline and reports `LIFT_UNAUTHORIZED` for a bad signature, another hold or placement, a lapsed validity, the lifter's own key or an unpinned key; `-require-lift-authorization` makes a lift with none a finding too. Placing a hold needs no second person.
  - *Open.* A hold stops only bide's own erasure, not a database administrator or a restore. Trail signing from the command line uses a key file; HSM and KMS signing go through the library. Sessions cannot be redacted. See the retention guide and KNOWN-LIMITATIONS.

- **A kill switch (experimental).**
  - *Stopping.* `bide stop` (and `bide-hsm stop` for a key in an HSM or a KMS) sets a stop by scope (`-all`, `-tool`, `-flow`, `-agent`), lists, shows and lifts it. An agent given a `StopSwitch` (and a plan flow given `WithStopSwitch`) holds a covered run at a drive's start, a turn's start, before a call's claim, after the claim and immediately before the call begins. A call that has begun finishes and is journaled; a saga's rollback continues unless the stop blocks compensation. A side-effect call that cannot read the control run, or cannot judge it, is held. The check points are in model 16 (`spec/tla/stop`).
  - *Two modes.* Basic mode trusts the store: anyone who can write it can stop and lift. Audited mode counts only records signed by approvers of the pinned policy, lifts by a quorum of distinct lifters, and walks signed policy transitions from a pinned root. A stop that cannot be judged is held, not dropped.
  - *Evidence.* An audited control writes every signed record to a stop trail that is signed and anchored like any other. `bide audit stops` checks the trail against the policy and the control run; `bide-hsm audit stops -sign-head` signs its head with an HSM or KMS key. A record that reached one place and not the other is listed as unapplied and applied by a signed record (`bide stop -apply-pending`).
  - *Seeing and hearing of it.* `bide view` opens every page with a banner while a stop is in force, and also when the stops cannot be judged. `stop_set` and `stop_lifted` are notification kinds with the notifier's claim, acknowledgement, retry and escalation, so a stop is not lost with the process that set it. `bide audit notifications -db` checks that every stop in force was told, whatever time its record carries, since that time is the writer's own.
  - *Open.* A stop does not cancel a call that has begun. A writer with store write access cannot stop a stop from landing but can slow reads of the control run linearly by adding junk entries (measured with 100,000 entries: 0.84 s on SQLite, 2.0 s on Postgres for one `SetStop`; a guard test fails past 2 s with 10,000), so keep the control run writable only by the processes that operate the kill switch. Basic mode trusts store access completely. A stop set and lifted with both times backdated, as the first records of the control run and never told, goes unnotified; the records stay in the control run (`bide stop -list`). The reaction time depends on the poll interval (default 1s) and the staleness bound (default 15s), which the model does not cover. The full list is the Kill switch section of KNOWN-LIMITATIONS.

- **Locked anchors in S3 and Google Cloud Storage (experimental).** The S3 anchor comes first, then the GCS anchor described after it.

  *S3.* Module `anchor/awss3` is the first production `audit.Anchor`. It writes each signed tree head as an object under S3 Object Lock (compliance mode by default; governance only with `AllowGovernance`), reads it back, and refuses a bucket whose lock, retention, versioning or encryption is weaker than configured. `bide-anchor verify`, `export` and `check` verify the objects offline or with read-only credentials. It is tested against MinIO and a fake, never against AWS. An anchored head carries the run or trail ID, which cannot be erased before the retention date, so IDs must hold no personal data. The timestamp is S3's clock, not an RFC 3161 token. The object layout, body and checks it shares with later object-store anchors now live in the new `audit/anchorobj` package (experimental); `anchor/awss3` uses it with no change in behaviour, and its tests pin the object keys and bodies byte for byte.
  - *Fewer heads.* `AuditedStore.WithMinInterval` and `AuditedEventStore.WithMinInterval` publish at most one head per run or trail per interval, so an anchor that keeps every head for years does not receive one per write. A run's first head, its end marker, `Reanchor` and `Flush` publish at once. A process that dies loses its timers, and what it held back stays unanchored until the next start or recovery pass (`ReanchorRuns`, `AnchorTrails`). `bide audit verify-decision-coverage` and `verify-receipts` now say which of a journal's last records are under no signed head, and `verify-decision-coverage -max-unanchored` fails on a tail whose newest head is older than a bound.
  - *Offline checks.* `bide-anchor verify`, `export` and `check` are now their own module, `github.com/bide-ai/bide/cmd/bide-anchor` (`go install github.com/bide-ai/bide/cmd/bide-anchor@v0.21.0`), with `-backend` naming the object store the anchor wrote to (`s3` is the default and the only one built in) and exit status 3 for an audit that was aborted. `LoadDir`, which `verify` and `export -dir` use, now fails on an empty directory (nothing to verify never passes) and on two validly signed heads of one size with different roots (equivocation), as the online reader already did; the directory walk and those checks live in `audit/anchorobj`. A directory copy still cannot show that it is complete: compare its newest head with the live bucket.
  *Google Cloud Storage.* Module `anchor/gcs` is the second production `audit.Anchor`. It writes each signed tree head as an object in a bucket whose retention policy is locked, with create-only writes, and reads it back, refusing a retention, Cloud KMS key, hold or checksum weaker than configured. Its reader lists noncurrent generations so a deleted or overwritten newest head does not hide it, errors on two different signed heads of one size and on a well-formed head with a bad signature, and reports what it skipped. `New` refuses a bucket owned by another project, without a locked retention policy of at least the configured length, versioning, uniform bucket-level access, enforced public access prevention or the configured default key. It ships least-privilege custom IAM roles (no delete, so no overwrite, and a separate hold-release identity). It was run once against a real bucket, by one person, and is otherwise tested against an in-memory model; a locked policy cannot be undone, so read the [runbook](https://github.com/bide-ai/bide/blob/v0.21.0/docs/testing/gcs-anchor-real-run.md) first. The same ID rule applies: a run or trail ID in an anchored head cannot be erased, so it must hold no personal data. See the [guide](https://github.com/bide-ai/bide/blob/v0.21.0/docs/guides/anchoring-gcs.md) and the Anchoring: Google Cloud Storage section of KNOWN-LIMITATIONS (what a project owner can do after the retention, what was and was not verified).

- **Build provenance for the release (SLSA Build Level 3).** From v0.21.0-rc.1, and in this release, every archive, archive SBOM, `checksums.txt`, `approve-page.SHA256SUMS` and the module set SBOM carries a SLSA v1 provenance attestation. The files are built, and the attestation is made, by reusable workflows of a separate repository, [bide-ai/release-builder](https://github.com/bide-ai/release-builder), which `release.yml` pins by full commit SHA. The build job runs bide's build steps with a read-only token and no OIDC token; a second job, which runs none of bide's code, makes the attestation. Provenance made by those steps cannot be forged by anything in bide's repository, which is the Level 3 claim and its whole scope. The release workflow verifies every file's provenance before it signs or publishes and fails the release if one does not verify. Releases before v0.21.0 have no provenance attestations. The cosign signature identity is unchanged.
  - *To verify.* Use `gh attestation verify <file> -R bide-ai/bide --signer-workflow bide-ai/release-builder/.github/workflows/build.yml --source-ref refs/tags/vX.Y.Z --predicate-type https://slsa.dev/provenance/v1 --deny-self-hosted-runners`. For the strictest check also pass `--signer-digest` (the commit of a `v*` tag of the release builder, listed in its README, not merely the commit `release.yml` names) and `--source-digest` (the tag's commit). The module set SBOM is attested by the builder's `module-sbom.yml`.
  - *What it does not show.* That the source is free of defects or that bide's build steps are benign (the provenance says which commit was built); anything about an administrator of the builder repository or of GitHub; and the release workflow's own check is a safety net, not the control, since a malicious tag could change it. The control is the verification you run. We have not exercised an offline verification with a downloaded bundle. See [verify releases](https://github.com/bide-ai/bide/blob/v0.21.0/docs/trust/verify-releases.md).

- **Fixes and smaller changes.** The relay's state file write retries when Windows has the file open and no longer forgets a failed save. `release.sh --push` waits for main's CI instead of failing at once, `release.sh --assemble-changelog` accepts a candidate version and warns when a final is assembled after its candidate, the release's `go mod tidy` no longer fails on a test that imported the pgx driver directly (CI now checks `go mod tidy` in every module), and a pre-release tag (`vX.Y.Z-rc.N`) is accepted by the module SBOM check, marked a pre-release and given no Homebrew formula. `bide edit` says when git did not answer within its 15 second deadline, instead of "signal: killed", and no longer waits on a helper a git left holding its pipes. A relay test that timed a retry now asserts structure instead of a duration (test change only). A kill switch stop is now named by scope, compensation and a generation, so two operators who set the same scope at once cannot leave it in force twice. The `bide check` warning for a quoted `assert` name with a backslash now reads as guidance. New pages: a [code map](https://github.com/bide-ai/bide/blob/v0.21.0/docs/ARCHITECTURE.md) and the control mapping.

API changes:

- Added: `audit.RedactionReport.Ended`; modules `anchor/awss3`, `anchor/gcs` and `audit/anchorobj` (experimental) and the `bide-anchor` command, now its own module with `-backend`; `AuditedStore.WithMinInterval`, `Flush` and `Pending`, `AuditedEventStore.WithMinInterval`, `OnRecovered`; `audit.NewLiftAuthorization`, `LiftAuthorization`, `WithLiftAuthorization`, `WithLiftAuthorizers`, `RequireLiftAuthorization`, `ErrLiftUnauthorized`; `agent.StopControl`, `StopPolicy`, `StopRecord`, `StopSwitch`, `WithStopSwitch`, `*Stopped`, `WithRecoverStop`, `StopNotifier`, `WithNotifyStops` and the notification kinds `stop_set` and `stop_lifted`; `agent.Redactor`, `Holder`, `Compactor`, `PlanRedaction`, `Redact`; `audit.RedactJournal`, `VerifyRedactions`, `PlaceLegalHold`, `LiftLegalHold`, `AcknowledgeRecord`, `NewStopTrail`, `VerifyStops`, `SignStopTrail`; `audit.CertApprover.CheckCertificate` and the `CertIdentity` accessors; `audit.PlainDistributionPoints` and `CRL.DistributionPoints`. The generated [API reference](https://github.com/bide-ai/bide/blob/v0.21.0/docs/reference/api/index.md) lists every new symbol.
- Added, commands: `bide journal redact|hold|acknowledge` (hold has `place`, `lift`, `list` and `authorize`), `bide-hsm journal`, `bide audit verify-decision-coverage -max-unanchored`, `bide audit redactions|stops`, `bide stop`, `bide identity check`, `bide approve -item`, `bide-hsm csr|stop`, `bide keygen -cn`, and `-stop-policy`, `-stop-root` and `-stops-within` on `bide audit notifications`.
- Changed: the kill switch, redaction and legal-hold symbols are labelled experimental in the API reference; a kill switch stop's record name; a CRL with a URI-only issuing distribution point is read; `agent.RedactionProtected` no longer lists the end markers.
- `audit.VerifyNotifications` takes the control run's state (`NotifyVerifyInput.Stops`) and reads the `stop_set` and `stop_lifted` kinds, which it refused as unknown before.

Upgrading:

- **Postgres and erasure.** The migration creates `bide_redact_v3` and the `bide_holds` table and revokes `EXECUTE` on every older `bide_redact_vN` from every role. Run it as the schema owner and grant the erasing role `EXECUTE` on `v3`. The function needs a transaction at `READ COMMITTED`. A schema or SQLite file from before holds has no hold. Only deployments that use `bide journal redact` need this.
- **Kill switch.** The run ID `@stop` is reserved: no user run may use it, and recovery does not drive it. A store whose control run holds a record needs an agent built with a `StopSwitch`, or its drives fail with `ErrConfig`. Moving a deployment to audited mode needs the policy on every process first; a process left basic holds covered calls. A stop written by an older version (named by its content) is read as before, but two older writers can still leave one scope in force twice.
- **Journals.** The journal format tag is unchanged (`bide.journal.v1-dev`), so before 1.0 finish or resolve runs before you upgrade, as for every pre-release.
- Nothing else changes for existing flows and gates. The kill switch, erasure and anchor are opt-in.

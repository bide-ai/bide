# Design: a browser page for approving a call

Status: proposed, for review. Nothing in this note is built. It follows the approval intake
(`approvals.Handler`, [Taking decisions over HTTP](../guides/hitl-approval.md#taking-decisions-over-http)),
which already takes a signed decision over HTTP and shows a pending call read-only. The page is the
client that lets an approver who has no `bide` binary sign one.

## Goal

An approver opens a link from a notification, sees exactly what they are about to approve, and signs
the decision in the browser, with a key that never leaves it. The application records it through the
intake and signs the audit log as it does for any decision. Non-goals: login, sessions, a server-held
key for the approver, an approve link that decides on a click, a design for roles or delegation.

## What the page must guarantee

1. **What is signed is what is shown.** The signature binds the SHA-256 of the canonical arguments
   (`agent.ApprovalDecisionBytes`). The page computes that digest itself, from the arguments it
   displays; it does not sign the server's `args_sha256`. If it did, a server could show arguments A
   and supply the digest of B, and the approver would sign B having read A. The page shows the digest
   it computed and compares it to `args_sha256` as a check on the endpoint, not as the thing signed.
2. **The key is not extractable.** An Ed25519 key pair is generated with WebCrypto
   (`extractable: false` for the private key), stored as a `CryptoKey` in IndexedDB, and used only to
   sign. Script on the page can ask it to sign; it cannot read it out.
3. **A notification links only to a read-only page.** The link carries a run id and a call id and
   nothing else: no token, no verdict, no signature. Opening it decides nothing. A decision needs a
   deliberate act on the page, after the call is displayed.
4. **Nothing the page needs to be trusted for is in the endpoint's trust path.** The endpoint
   verifies the signature against the recorded call and the enrolled key regardless of which client
   produced it, so a compromised page can produce a decision only with a key the browser lets it use
   (see "What the browser key does not protect against").

## Flow

1. First use: the page generates the key pair, stores the private `CryptoKey`, and shows the public
   key as `ed25519:<hex>` (the text `bide keygen -as` prints and the approver-keys file holds). The
   approver sends it to whoever enrolls keys; nothing is signed until it is enrolled, since the
   endpoint refuses an approver with no key.
2. The link opens `GET <mount>/` (the page) with `?run=&call=` in the fragment (`#`), so the ids are
   not sent in a `Referer` and are not in server logs. The page fetches `GET /pending`.
3. It renders the call: the run, the tool, **all** of the arguments, the gate (k of n, who decided,
   who is pending), and the digest it computed. It refuses to enable signing if the call is not
   `waiting`, the approver is not on the gate, or the approver already has a counted decision.
4. The approver types their approver id to confirm (as `bide approve` does; Approve and Reject are
   separate, and Reject says REJECT). The page signs `ApprovalDecisionBytes` for the displayed
   subject and `decided_at` from the browser clock, and POSTs to `/decisions`.
5. It shows the gate's new standing from the response. A replay (reload, double click) is a no-op.

## Decisions this design makes

**Canonical arguments in the browser.** The digest is over the canonical arguments: parsed as JSON,
keys sorted, no insignificant whitespace, no HTML escaping, number literals kept verbatim. JavaScript's
`JSON.parse` loses number spelling (`1.0`, `1e3`, large integers), so the page needs its own small
parser that keeps number text. The risk is a divergence from Go that makes valid signatures fail to
verify (safe) or, worse, two different arguments that canonicalize alike. Mitigation: a golden file
of vectors (arguments, canonical bytes, digest) generated by Go and consumed by both the Go tests and
the page's tests, plus a fuzz target that compares the two on generated inputs. The page's tests run
under Node's `node:test`, which has Ed25519 in `crypto.subtle`, with no npm dependency.

**Display that cannot hide content.** The CLI refuses to sign arguments it truncated, and the page
does the same: it shows all of them, in a monospace block set with `textContent` (never `innerHTML`),
and escapes control characters, bidirectional overrides and zero-width characters visibly, as
`bide approve` does. A very long value is shown in full behind a scroll, and signing stays disabled
until the approver has scrolled to its end.

**Same-origin, locked down.** The page and the API are served by the same handler under one origin
(`approvals.WithPage()`, off by default), so IndexedDB's origin scoping is the key's scope and no CORS
is needed. The page is one HTML file and one script, embedded in the package (`embed`), with
`Content-Security-Policy: default-src 'none'; script-src 'self'; connect-src 'self'; style-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`,
no inline script, no third-party code, and `Cache-Control: no-store` for the page and `Referrer-Policy: no-referrer`.

**Ed25519 only.** WebCrypto's Ed25519 is in current Chrome, Firefox and Safari; the page checks for
it and says so when it is missing. ML-DSA and hybrid are not available in browsers, so a browser
approver is an Ed25519 approver. Nothing in the endpoint changes.

## What the browser key does not protect against

- **Script on the origin.** A non-extractable key can still be used by any script that runs on the
  page. Cross-site scripting on that origin could ask the key to sign. The CSP above is the defense;
  the typed confirmation is not, since script can type. This is the main residual risk, and it is why
  the page is a static file with no dependencies and no templating of server data into script.
- **Browser or device compromise,** which has the key whether or not it is extractable.
- **Key loss.** IndexedDB can be cleared by the user, by the browser's storage pressure, and, in
  Safari, by the browser after seven days without a visit for a site that is not an installed web
  app. A lost key means a re-enrollment (a new key under the same approver id: old decisions still
  verify with the old public key, which must be kept). The page warns of this at first use and
  recommends installing it.
- **Two devices.** A seat is a key, and an approver id holds one. A second device is a rotation, not
  a second key, unless the operator enrolls it under a second approver id on the gate.

## Alternatives considered

- **WebAuthn / passkeys** hold the key in hardware and ask for a user gesture per signature, which
  is stronger against script on the page. They sign `authenticatorData || SHA-256(clientDataJSON)`
  with the decision bytes as the challenge, not the decision bytes themselves, so they need a new
  signature scheme in `agent.ApproverVerifier` (`webauthn-es256`) that the gate, `TallyApprovals`
  and `audit.VerifyApprovals` verify, and a new offline verifier path. That is a larger protocol
  change than a page, and it would be its own design. Recommended as a later step, not as part of
  this page.
- **A server-held key per approver** (the page logs in and the server signs) would make the
  application the signer of approvals, which defeats the property that the approver's signature is
  independent evidence. Rejected.
- **Approve links in notifications** (a click decides). Rejected, as the
  [notifications guide](../guides/notifications.md) says: a link that decides on a click is a
  phishing target.

## Build plan

1. Test vectors for canonical arguments, generated by Go (`agent/testdata`), and a Go test that
   pins them (this also pins the encoding for any other language's verifier).
2. The page: parser and canonicalizer, WebCrypto key handling, display, POST. Node tests against the
   vectors and against the real handler (an `httptest` server driven by a Node script, or the same
   checks ported to Go for the server half).
3. `approvals.WithPage()`: embedded assets, the headers above, and a test that every response of the
   page carries them.
4. Docs: the guide section, the known limitations above, and the approver-keys enrollment step.

## Decisions for review

1. Build the page at all, given the residual risk from script on the origin? Recommendation: yes,
   with the CSP and no dependencies, and state the risk in the guide.
2. Sign the digest computed in the browser (this design) at the cost of a second canonicalizer?
   Recommendation: yes; the alternative breaks "what you see is what you sign".
3. WebAuthn as the follow-up rather than part of this? Recommendation: yes, as its own design.
4. Ids in the URL fragment rather than the query? Recommendation: fragment.
5. Is one device per approver id acceptable for the first version? Recommendation: yes.
